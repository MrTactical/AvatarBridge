## The live tissue's first compile was slow, and a shader that timed out passed the check. FIXED ON DEV 2026-11-07
*Moved from `Unfinished.md` item 32.14 the same day. Joe, 2026-11-07: "fix the compile... and then
the check that should catch the failed shader that missed it both times"; "it could be us, not
Poiyomi Pro, because we know Poiyomi Pro on default compiles just fine".*

**What the corpus re-time found** (2026-11-07, dev `a9bb10b`, squash and tissue on, 15 avatars).
Per shader, the first time: 58-98 s on Poiyomi and Poiyomi Toon, 134-202 s on Poiyomi Pro. Six
first conversions took 6 min 38 s to 79 min. On both Poiyomi Pro avatars one clothing layer's
shader timed out (Base, Add and ShadowCaster vertex programs), and the first part's pass put the
material on it anyway ("14 of 14", "35 of 35"); only the second part's check saw the error.

**Withdrawn**, both from the queue item: "checked with `ShaderHasError`, which compiles it" (the
check costs 0 ms and compiles nothing), and "the material's own keyword variants compile later, on
use, and those are the ones that timed out" (the timed-out compiles carried no lighting keyword:
they were the default variant).

**It was ours.** fxc on the Base vertex program of the shader that timed out, one at a time:
stock Poiyomi Pro 0 s, with the squash 11 s, with the squash and the tissue 32-41 s.

**Why the check missed it** (`Dev/Probes/Perf/TissueCompileProbe.cs`, batch, copies of real
materials, each step timed):
- The import compiles too little to tell. A plain HLSL error is refused there (an undeclared name:
  refused at import, nothing worn), but a copy comes back with no warning at all; the full compile
  happens when a material wears it (old code: patch and import 9-16 s, the wear 128-143 s, the
  warnings appearing only after the wear). The check ran between the two.
- An error only the full compile finds: an unroll failure, made by bloating the tissue include,
  passed the import's check and was refused by the new one.
- A timeout itself could not be forced: the bloated include rolled compiled for 292 s without one,
  so Unity's limit is past five minutes for a compile on a quiet machine. The overnight timeouts
  came under the corpus run's load. The new check catching one rests on the corpus run's second
  part, whose check did see the error once the wear's compile had made it.

**The fix.**
- `yaps_jelly.cginc`: each state read takes all four slots' textures, the three others off the
  texture where a Load returns 0, instead of a branch per read; the hands', limbs' and plug
  lights' loops rolled. fxc Base vertex 32-41 s to 20-22 s (neither alone did much: 28 s and 33 s).
- `YapsShaderPatcher.Compiled`: every pass of a fresh or reused copy is compiled on a stand-in with
  the material's keywords before the error check, so the wear that follows compiles nothing (1-4 ms
  after it, against 128-143 s). A copy that fails is refused with Unity's reason; the tissue keeps
  that material on the squash alone and the report warns, naming it.
- Same probe conditions (12 of 16 cores, below normal), cold cache, first compile per material:

  | | Old code | New code |
  |---|---:|---:|
  | Poiyomi Pro, three materials (new code: three runs) | 138-156 s | 27-49 s |
  | Poiyomi Toon, three materials | 77-99 s | 32-34 s |
  | The second avatar's material that timed out | timed out | 31 s |
  | Converting again, the copies already in the project (a second launch) | | 0.7-1.1 s |

  The same text written as a new file (the copies moved out between two launches, which no
  conversion does) compiled again in full, 28-47 s.

**The stricter check refuses nothing that drew.** Every corpus log since squash (425 to 429, and the
tissue re-time) holds no shader error on a YAPS copy but the two timeouts, and those logs are the
wear's full compiles. The worry that pulled compiling every pass before (`04be99c`: the caster
compiles there and could refuse a copy refused nowhere) had nothing behind it.
